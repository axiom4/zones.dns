# Changelog

## Unreleased
- **Upgrading:** run `manage.py migrate` (new tables `DhcpReservation` and `MacVendor`; migration 0034 also copies the `DHCP*` settings of `.env` into the database, once), then `manage.py update_oui` once to fill the vendor table (about 52,000 blocks). Restart `rundns` and gunicorn, publish the new GUI build. `INSTALL.md` changed how port 53 is given to Python (see Security).
- **Added**
  - DHCP reservations in the GUI (*DHCP > Reservations*): a fixed IPv4 address for a MAC (host name and note optional, on/off switch), a *Reserve* button on every DHCPv4 lease, CSV import (`hostname,mac,ip` with optional note and enabled; a header line allows any column order; `,` `;` or tab; preview; *Replace* needs the second factor, step-up scope `dhcp-replace`; any error in the file changes nothing) and export. `rundhcp` reads the table live, no restart; `DHCP_RESERVATIONS` in `.env` still works. The address must be inside a served network. API: `/api/dhcp/reservations/` (+ `export/`, `import/`).
  - DHCP settings saved in the GUI apply at once: `rundhcp` notices the change (within 2 s) and starts again with the new values after checking them; invalid ones are reported on stderr and the old ones keep running; switching `DHCP` off stops it. No more manual restart.
  - DHCP leases: the *Leases* tab shows only the DHCPv4 leases; the DHCPv6 ones (addresses and delegated prefixes) are in the new *Leases 6* tab. A DHCPv6 lease now shows the MAC address read from the client's DUID (types 1 and 3 over Ethernet), the maker of the network card and the host name the same MAC has in DHCPv4 (lease or reservation); the full DUID is the tooltip. API: new field `mac` on `/api/dhcp/leases/`.
  - DHCPv6 reservations (*DHCP > Reservations 6*): a fixed IPv6 address (IA_NA) for a client, named by its DUID; the address may lie outside the pool but inside `DHCP6_PREFIX`, and nobody else is given it. A *Reserve* button on every DHCPv6 address lease fills the form. `rundhcp` reads the table live. A change of the reserved address makes the client's renewal fail (NoBinding) so it asks again and gets the new one. CSV import (preview; *Replace* needs the second factor, like the IPv4 one) and export, columns `duid,ip,note,enabled`. Delegated prefixes (IA_PD) are not covered. API: `/api/dhcp/reservations6/` (+ `export/`, `import/`). Run `manage.py migrate`.
  - *DHCP > Neighbours*: one row per host (MAC address) with all its IPv6 addresses (a host usually has a DHCPv6 one, a SLAAC one, privacy ones and a link-local one); the IPv6 hosts this server sees on the network (kernel neighbour table, `ip -6 neigh`, on `DHCP_INTERFACE`), with MAC address, the maker of the card, the name the same MAC has in DHCPv4 and where the address comes from (DHCPv6 lease, SLAAC built from the MAC, privacy or fixed, link-local). Hosts that configure themselves (SLAAC, Android) have no lease and appear only here. Ping and Ping all as in the leases. Linux only; empty elsewhere. API: `GET /api/dhcp/neighbors/`.
  - DHCPv6 leases remember the client's MAC address and host name. The MAC comes from the DUID (types 1 and 3) or, for the others (Home Assistant and other systemd clients use type 4, with no MAC in it), from the link-local address the client wrote from: read from an EUI-64 address, else from the kernel's neighbour table (`ip -6 neigh`, Linux; a privacy address not in the table yet is found at the next Renew). Not for relayed messages. The host name comes from the Client FQDN option (39), when the client sends one. Run `manage.py migrate` (0036).
  - DHCP names (`DHCP_NAMES`) now include DHCPv6: `<name>.<DHCP_DOMAIN>` answers `AAAA` with the addresses (IA_NA) of the client, next to its `A`, and the reverse name (`ip6.arpa`) answers `PTR`. A DHCPv6 lease has a name when the client sent one (Client FQDN) or when its MAC has one in DHCPv4. Delegated prefixes are not hosts and get no name. A name whose leases are of the other family only (say a Home Assistant with a fixed IPv4 and a DHCPv6 lease) is answered for the family it has and forwarded to the upstream for the other, instead of an empty answer. Zones, static hosts and DHCP leases are merged per type: a record of the zone or a static host wins for the type it has, the leases fill in the other (a zone `A` with a DHCPv6 `AAAA`, or the reverse); a client still cannot take over a type the zone already has.
  - DHCP settings live only in the database (GUI: *DHCP > DHCP settings*); the `DHCP*` lines of `.env` are no longer read, `.env.example` has none. `manage.py migrate` copies once what `.env` sets (a value already saved in the GUI stays); after that delete the `DHCP*` lines from `.env`. Until DHCP is turned on `rundhcp` waits instead of exiting. `settings.py` keeps only the defaults.
  - MAC vendor: the maker of a network card is shown next to every MAC in the leases and the reservations, and under the MAC field of the reservation form. It comes from a table in the database (`MacVendor`, IEEE registry via Wireshark's `manuf`, 24/28/36-bit blocks; downloaded by `manage.py update_oui`, nothing is shipped with the code), nothing is sent to the Internet; random (locally administered) addresses are labelled as such. `manage.py update_oui` replaces the table in one transaction (the old one stays if the download fails); schedule it nightly in cron (`INSTALL.md`). API: `GET /api/dhcp/vendor/?mac=`.
  - Ping: a *Ping* button on every lease and reservation and *Ping all* on both lists show whether a host answers and its round trip time. The server builds and sends the ICMP echo itself (IPv4 and IPv6) on an unprivileged ICMP socket, or a raw one with `CAP_NET_RAW`; only if the system allows neither it runs the `ping` program; only private, link-local and unique-local addresses are accepted and at most 64 per request. A double click on *Ping* opens a window that pings every second and prints what the `ping` command prints (reply size, `icmp_seq`, `ttl`, `time`, and the statistics block on *Stop*) in a text box that can be copied. API: `POST /api/dhcp/ping/` (`up`, `ms`, `ttl`, `bytes`). A host that drops ICMP shows "no answer" even if it is up.
  - Statistics count the DNS daemon and the filtering proxy together (one chart, one set of totals and top lists; in the chart DNS queries are violet and blocked ones red, proxy requests teal and blocked ones amber); a selector shows *DNS + proxy*, *DNS only (blacklist)* or *Proxy only*. The proxy's requests appear as *Through the proxy* and *Pages cleaned* (its blocks join *Blocked*), its HTTP methods next to the query types. API: `source=all|dns|proxy` of `GET /api/stats/`.
  - Proxy > Settings > *External ad-block lists*: lists in EasyList / Adblock Plus syntax (`PROXY_RULE_LISTS`, `name=https://…`, e.g. EasyList and EasyPrivacy) are downloaded by `runproxy` every day, by `manage.py import_blocklist` (the same command and cron job as the blacklists) or at once with *Sync now*. The proxy applies the domain rules (`||domain^`), the exceptions (`@@||domain^`) and the element-hiding rules (`##selector`, at most 5000 generic ones); URL fragments, regular expressions and rules with browser-only options are skipped. A list that fails keeps its last good rules and shows the error. API: `GET/POST /api/proxy/rules/`.
  - HTTP / HTTPS ad-blocking and popup-blocking proxy (`manage.py runproxy`, GUI: the *Proxy* section, Settings and Logs; API `/api/proxy/…`; the old page addresses `/dhcp/proxy` and `/dhcp/proxy-logs` redirect there):
    - **DHCP WPAD auto-assignment (`DHCP_WPAD=true`, `DHCP_WPAD_URL`):** DHCPv4 sends option 252 (`http://<DHCP_SERVER>:<PROXY_PORT>/wpad.dat`, or a custom URL) and the DNS daemon answers `wpad.<DHCP_DOMAIN>` and `wpad.<DEFAULT_ZONE>` with `DHCP_SERVER` (`via: WPAD (DHCP)`), while still preventing any DHCP client from claiming the `wpad` host name. The generated PAC script (`FindProxyForURL`, served at `/wpad.dat` and `/proxy.pac` both by Django/nginx on port 80/443 — exempted from `SECURE_SSL_REDIRECT` and `ALLOWED_HOSTS` checks — and directly on the proxy port) bypasses private networks, internal domains and `@@domain` exceptions, and routes HTTP/HTTPS traffic through `PROXY <server>:<port>; DIRECT`. Includes a one-click Apple Configuration Profile (`/proxy.mobileconfig`) for macOS and iOS that configures both the PAC proxy URL and the Root CA certificate.
    - **Domain, URL and HTML page filtering (`PROXY_BLOCK_ADS`, `PROXY_BLOCK_POPUPS`, `PROXY_CUSTOM_RULES`):** shares the Zones.dns Blacklist (Personal blocks, regex patterns, allow exceptions and Public lists) and blocks ad and popup/popunder URLs (`AD_URL_RX`, `POPUP_URL_RX`) and custom rules (`/regex/`, substring). On `text/html` responses (`gzip` and `deflate` decompressed), strips blocked `<script>` and `<iframe>` tags and inline popup scripts (`PopAds`, `popunder`, `aclib.runPop`...), injects cosmetic CSS rules (`<style id="zones-adblock-css">`, plus global `##selector` and per-domain `domain.com##selector` rules) and injects an early popup/popunder blocker (`<script id="zones-popup-blocker">` guarding `window.open`, transparent click-hijacking overlays and `beforeunload` traps).
    - **HTTPS modes (`PROXY_HTTPS_MITM`):** off by default (`CONNECT` tunnel: blocks blacklisted, ad and popup domains on HTTPS without requiring any certificate on clients). When `PROXY_HTTPS_MITM=true`, generates a local ECDSA P-256 Proxy Root CA (stored in `Setting`, downloadable at `/proxy-ca.crt`, `http://<server>:<port>/ca.crt` or from the GUI) and dynamic per-host leaf certificates to filter HTML and block popups inside HTTPS pages as well. Restricted to `DNS_ALLOW_QUERY` clients, with SSRF protection against loopback and link-local targets. API: `GET`/`POST /api/dhcp/proxy/info/`, `POST /api/dhcp/proxy/test/`. Run `manage.py migrate` (0037: `Setting.value` widened to `TextField` for PostgreSQL/MySQL).
- **Fixed**
  - DNS over HTTPS answered `406` to clients that send `Accept: application/dns-message` (Firefox, Chrome): `/dns-query` is now a plain Django view.
  - `rundns`: a database error during the hourly log purge ended the whole daemon; it is now reported and retried an hour later. `SIGTERM` (supervisor stop) saves the log rows still waiting, like Ctrl-C.
  - With the database away, a name whose blacklist answer was not in memory got no answer at all: it is now answered unblocked until the database is back.
  - DNS over TCP answered only the first query of a connection and dropped the others (DNS over TLS clients reuse the connection). One thread now reads every connection and hands each complete query to the workers: a connection serves any number of queries and costs a worker only while one of them is answered, so clients that keep theirs open (or send nothing) no longer use up `DNS_WORKERS`. It is closed after 10 s of silence or 5 minutes in all (1000 at most, then the one silent the longest goes), and a client outside `DNS_ALLOW_QUERY` is closed before anything is read. Answers of one connection may leave in another order than the queries (RFC 7766 §7).
  - Suspicious queries: a flood of random subdomains from one client made every query scan a growing table under a lock (20,000 names: seconds). The table stops at `SUSPICIOUS_MAX_UNIQUE`.
  - Query log: `hours` with a huge or non-ASCII number gave error 500; `hours=0` listed nothing while counting everything (now: the whole log).
  - DNS UPDATE: records are checked like the API's (a record the daemon could not build is refused with `FORMERR`), a TTL of 0 takes the default instead of failing.
  - A blacklist answer worked out while the data was being reloaded could be remembered after the reload (an unblocked name stayed blocked up to `DNS_DATA_TTL`).
  - Records: a duplicate is refused by the API, and a CNAME that shares its name with other records is refused everywhere (API, Django admin, zone file import, *Sync PTR*; a DNS UPDATE ignores it, RFC 2136 §3.4.2.2).
  - With the database away the names of DHCP clients are answered as unknown instead of not at all, and with `DNS_LOG_FLUSH=0` the query is answered without its log row. The daemon says so on stderr once a minute.
  - Rate limit: only the first refused query of a window is logged (a flood filled the log), and IPv6 clients are counted per /64 (a host that changed address inside its network started from zero).
  - Upstream answers over UDP are taken only from the address and port that were asked, and a packet with another id is skipped instead of ending the wait.
  - Blacklist patterns: a pattern is also tried, in a separate process and for 2 seconds at most, on names made to slow it down; `a*a*a*a*a*a*b` has no nested repeat and was accepted.
  - DHCP: a standby server (`DHCP_FAILOVER_SECS`) answered `NAK` to a client that came back asking for the address the primary had given it (now silence, RFC 2131 §4.3.2); a DHCPv6 Release or Decline with thousands of IAs ran a query for each (now 8, like the other messages); the old leases were forgotten only after an hour without any packet, which a network in use never has.
  - Domain audit and map lookups failed when `UPSTREAM_DNS` carried a port (`127.0.0.1:5335`); a web server that answered a byte at a time could hold an audit request for hours (now 15 s in all per response).
  - Two step-up grants issued in the same second for the same action were the same text: the second was refused as already used.

- **Security**
  - Emptying a zone asks for the second factor like deleting it: *Import* with *Replace* and a bulk delete of every record of a zone need the `zone-delete:<id>` grant (`X-MFA-Grant`). So do switching a zone off and a bulk delete of 10 or more records that are over half of the zone; purging the query log needs the new scope `log-purge`.
  - Opening the Django admin asks for the second factor (step-up scope `admin`): with a stolen token alone the admin could delete the owner's authenticator.
  - `DNS_PROXY_PROTOCOL` (off by default): DoH and DoT clients keep their own address for `DNS_ALLOW_QUERY`, the rate limit, the suspicious-query count and the log, instead of sharing 127.0.0.1. Needs `proxy_protocol on;` in `dns-dot.conf` and `X-Real-IP` in the `/dns-query` location (both in `deploy/nginx`).
  - `INSTALL.md`: `setcap` goes on a private copy of the interpreter, not on `/usr/bin/python3.x`, where it gave every local user the right to bind low ports (and raw sockets with DHCP).
  - Proxy, request smuggling: the client's `Content-Length` is never forwarded (next to a chunked body it let a second request ride on a shared upstream connection, and its answer reach another user). Chunk sizes must be hex digits (`-1` read without limit), `Transfer-Encoding` other than `chunked` and conflicting `Content-Length` values get 400 (RFC 9112 6.1, 6.3, 7.1). Bodies over 1 MB are streamed upstream instead of held in memory.
  - Proxy: `CONNECT` only to the ports of `PROXY_CONNECT_PORTS` (default `443,80,8443`; RFC 9110 9.3.6); the server's own addresses only on ports 80 and 443; at most 256 connections per client address.
  - Proxy: a POST, PATCH or streamed upload is never retried nor sent on a pooled connection (RFC 9110 9.2.2: it could be done twice).
  - Proxy log: query values are dropped (`?code=…`): they carried sign-in codes and keys. Older rows keep them: purge the proxy log once.
  - Proxy: HTML is decompressed at most up to 8 MB (a gzip bomb took all the memory); a larger page is relayed unfiltered.
  - Proxy Root CA: the private key is stored encrypted with a key derived from `SECRET_KEY` (an existing key is encrypted at the next start) and is no longer listed in the Django admin; new CAs last 5 years instead of 10. Changing `SECRET_KEY` now makes a new CA, to install again on the clients. `/proxy-ca.crt` and `/proxy.mobileconfig` are redirected to the https GUI (over plain http anyone on the path could swap the certificate); `/wpad.dat` stays on http.
  - Changing HTTPS inspection, WPAD (`DHCP_WPAD`, `DHCP_WPAD_URL`) or the proxy address or port, and making a new Root CA, need the second factor (new step-up scope `proxy-change`).
  - External ad-block lists: https only (also after a redirect).
  - Proxy with HTTPS inspection: upstream certificates are checked for revocation (the browser sees only the proxy's certificate and cannot). CRL first (it does not tell the CA which site is visited), OCSP when there is no CRL; soft-fail like browsers and never delaying a connection: the answer is fetched in the background and a revoked certificate is refused from the next connection on (`PROXY_REVOCATION`, default on).
  - `/proxy.mobileconfig` can be signed (`PROFILE_SIGN_CERT`, `PROFILE_SIGN_KEY`, e.g. the GUI's https certificate): macOS and iOS show it as verified and a changed profile is refused.
  - Proxy: `http://[::ffff:<server address>]:<port>/` reached the server's own ports (the database too): addresses are compared as plain IPv4. A *New Root CA* is used by `runproxy` and every gunicorn worker at once (the old one, maybe leaked, kept signing until a restart); its leaf certificates are dropped.
  - Proxy, HTTP/2: a stream reset by the client stops its handler (rapid reset, CVE-2023-44487); a request body has 30 s per read, like HTTP/1.1; body the proxy did not read (a refused upload) gives its flow-control window back, so later uploads on the connection no longer stall for good.
  - Proxy, ad-block lists: a hiding selector with `{`, `}` or `/*` is skipped (it could add its own CSS to every inspected page and read what is typed); lists already stored are filtered when loaded.
  - DHCP names: a DHCPv6 client could take any name (the Client FQDN was not checked): the name of another host, answered next to its `A` with a matching `PTR`, or `wpad`. A name is refused, in DHCPv4 and DHCPv6, when it is reserved or held by another device's lease (either family) or by an enabled reservation of another MAC. DHCPv6 temporary addresses (IA_TA) respect the reservations too.
  - DNSSEC: a negative answer is never authenticated (AD) from a signed SOA alone (NSEC/NSEC3 denial is not checked); an RRset is secure when one of its signatures verifies (a rollover or an Ed448 signature next to a good one gave SERVFAIL); only unsupported algorithms or digests make it insecure, not bogus.
  - Domain audit: NAT64 (`64:ff9b::/96`) and IPv4-compatible (`::a.b.c.d`) addresses are judged by the IPv4 address inside (`64:ff9b::a00:1` counted as public).
  - MFA: a code with non-ASCII characters gave error 500 instead of counting as a wrong attempt. Without Redis the memory cache keeps 100,000 entries (was 300: the geo and stats pages pushed out wrong-password counters and used-ticket marks).
  - DHCP reservations export: a note starting with `=`, `+`, `-`, `@` is written with a leading `'` (spreadsheet formula injection); the import removes it again.
  - The GUI's token is in an HttpOnly cookie (`dns_token`, `SameSite=Strict`, path `/api/`) instead of `localStorage`: a script injected into the page can no longer read it and use it elsewhere. Requests that change something with the cookie need Django's CSRF header (`X-CSRFToken`, sent by the GUI). Scripts keep `Authorization: Token <key>` (the sign-in answer still carries the token). *Sign out* now ends the token on the server too (`POST /api/logout/`; before, it only forgot it in the browser). **Upgrading:** everyone signs in again once.
  - DHCP settings that send the clients' traffic or time elsewhere need the second factor (new step-up scope `dhcp-change`), like WPAD and the proxy: gateway (`DHCP_ROUTER`), DNS (`DHCP_DNS`, `DHCP6_DNS`), NTP, search domains, routes, PXE boot server and file, relayed subnets (`DHCP_SUBNETS`), the RA router lifetime and `DHCP_LEASEQUERY`.
  - DHCP Leasequery (RFC 4388, RFC 5007) is answered only to the addresses or networks of the new `DHCP_LEASEQUERY` (*DHCP settings*, IPv4 and IPv6): anyone on the LAN could read every host name and MAC, in DHCPv4 by writing its own address as relay agent. **Upgrading:** empty by default, so Leasequery is refused until you list your relay agents. DHCPv6 Leasequery is answered only when sent straight to the server, not inside a Relay-forward.
  - Switching off all the records of a zone, or most of them (10 or more and over half), in one bulk action needs the zone's second factor (`zone-delete:<id>`), like deleting them.
- **Changed** (GUI)
  - New look, light and dark (follows the system): flat panels, colour only for state, fonts bundled in the build (Atkinson Hyperlegible Next and Mono, nothing loaded from the Internet). A live trace in the top bar shows the queries per minute of the last hour and the block rate; it opens Statistics. **Upgrading:** `npm install` (two font packages), then rebuild the GUI.
  - Works on every screen: a side rail on desktop, a compact rail on tablets, a bottom bar (Zones, Devices, Blocklist, Logs, More) on phones. Sections renamed after what they do: Devices (DHCP), Blocklist, Traffic map, Domain check, Advanced admin.
  - Accessibility (WCAG 2.2 AA): contrast of text, focus ring, switches and borders; labels tied to every field, errors next to the field that failed; skip link, landmarks, page titles; charts with a text summary and keyboard readout; nothing only by colour.
  - Feedback: errors are shown above any open dialog (a failed DHCP settings save showed nothing); confirmations ("Reserved 192.168.1.50 for nas") with Undo for deletes instead of a question; the second-factor dialog says which action it confirms; form dialogs no longer close on a click outside and ask before discarding changes.
  - Logs and statistics: every filter is in the address (links and Back keep it), every figure opens the filtered log, a blocked row says which list or rule blocked it with a direct Allow, live refresh pauses while you work on the list. DHCP settings grouped by goal with plain labels; one device search for all DHCP tabs; a "Live" ping button; a "Set up a device" panel for the proxy CA.
- **Changed** (proxy)
  - `runproxy` is asynchronous (asyncio, one event loop): a connection no longer holds a thread, so the 512-connection ceiling is gone (256 per client address, 8192 in all). Settings, filters, the CA and HTML filtering run on 16 worker threads, name lookups on 32. HTTP/1.1 towards the client is parsed by h11 (framing, chunked bodies, `100 Continue`; requests with an unknown `Transfer-Encoding` get 501). **Upgrading:** `pip install -r requirements.txt` (new: `h11`, `h2`, `httpcore`, `anyio`), then restart `runproxy`.
  - HTTP/2 both ways. Inside an HTTPS inspection session the browser may choose h2 (ALPN): many requests share one TLS connection, with flow control both ways. Towards the servers the proxy speaks HTTP/2 or HTTP/1.1 as each server chooses, with one pool of kept-alive connections (httpcore).
  - A server that answers without a length is relayed chunked to HTTP/1.1 clients, which keep their connection, instead of closing it.
  - An unexpected error while serving a request answers 500 (and is logged) instead of leaving the client without an answer.
  - Large uploads (over 1 MB) are sent with `Expect: 100-continue` and the server's answer is read while the body is still going out: a server that refuses the upload (413, 401) has its answer reach the client instead of a 502. An answer sent before the end of the client's body is followed by a lingering close (RFC 9112 9.6), so the client reads it instead of a connection reset.
  - WebSockets inside HTTPS inspection pass through (handshake to the server, then the frames unchanged both ways) instead of turning inspection off for that host; HTTP/2 clients may open them on a stream (RFC 8441, extended CONNECT, announced with `SETTINGS_ENABLE_CONNECT_PROTOCOL`). The handshake goes to the server over HTTP/1.1.
  - The proxy reads the database only through its 2 database threads (plus its log writer): 3 connections however busy it is. The `max_connections` note in `.env.example` says so.
- **Added** (proxy)
  - The HTML filter reads the policies of `<meta http-equiv="Content-Security-Policy">` too, and decompresses `br` pages (brotli 1.2 or later, with the same 8 MB limit).
- **Fixed** (proxy)
  - RFC 9110: `Via` is added both ways; fields named in `Connection` are dropped; no second `Date` / `Server` on relayed answers; `Cache-Control: no-transform` pages are not filtered; no `100 Continue` to HTTP/1.0 clients; `OPTIONS` with `Max-Forwards: 0` is answered by the proxy. An upstream `Content-Length` next to `Transfer-Encoding` is dropped.
  - Plain HTTP clients keep their connection (keep-alive). Tunnels stay open through 30 minutes of silence (was 2), with TCP keep-alive: IMAP IDLE, push and WebSockets are no longer cut.
  - Proxy DNS: the record's TTL (30 s to 10 min, was always 10 min), failed lookups retried after 30 s (was 2 min), the next address of a name is tried when one does not answer.
  - HTML filter: a page whose charset is only in a `<meta>` tag is no longer damaged; nothing is injected that the page's `Content-Security-Policy` would block; the popup guard no longer removes the "unsaved changes" warning (`beforeunload`) nor blocks sign-in popups that open a sized window after a request.
  - MITM: one TLS session closed without a request (a browser preconnect) no longer turns inspection off for that host; two within 10 minutes do (an app that pins its certificate). Leaf certificates no longer claim `keyEncipherment` (RFC 5480).
  - Proxy: a cut-short or multi-part gzip/deflate/zstd page was filtered and sent truncated: it is relayed as it came. A request header sent twice keeps both values.
  - Proxy: a database that did not answer within 10 s dropped the request without an answer (the timeout was taken for the client's own; on HTTP/2 "Task exception was never retrieved") and stopped the settings watcher of `runproxy`. The blacklist check now waits 3 s at most and then lets the name through, like the DNS daemon (said once a minute); the rule lists keep the last ones loaded.
  - Proxy log: a TLS handshake sent to the plain proxy port (an `https://` link to the proxy, or a client set to use it as an HTTPS proxy) is logged as `TLS` with the site's name (SNI) and the reason, instead of `Bad request: illegal request line` with the raw bytes.
- **Fixed** (DNS, DHCP, sign-in, logs, GUI)
  - DNS: the TCP retry to the upstream looped forever at full CPU when the upstream closed in the middle of an answer (also in the domain audit), and had no overall deadline. Big answers over UDP were cut at 8 KB; an answer dnslib cannot read no longer marks the upstream down; a truncated (TC) answer keeps its question, so clients retry over TCP; clients without DO get no RRSIG/NSEC; negative answers are cached for the SOA TTL / minimum (RFC 2308), at most `DNS_CACHE_NEG_TTL`.
  - DNS UPDATE: deleting a name or an RRset at the apex leaves the zone's NS records, and the last NS is kept; a value-dependent prerequisite needs the exact RRset (RFC 2136 §3.2.3). A bad `DNS_DDR` makes `rundns` refuse to start instead of leaving every query unanswered.
  - Sign-in with `MFA_REQUIRED=true`: a new user who set up the first factor got "Sign-in session expired" and could not finish. A JSON array as body, a ticket or passkey name that is not text: 400 instead of 500. A regex blacklist entry with the name of a public-list domain gave 500.
  - Grouped query log: `count` was the number of queries, not of groups (empty pages at the end). `?before=²`, `?ids=²`, a huge `older_than_hours`, an impossible `since` date, a `Location` like `http://host:abc/`, a malformed RDAP date or vCard: no more error 500. A WHOIS server sending a byte at a time is cut after 15 s. `update_oui` unpacks at most 50 MB.
  - DHCP: a client whose DUID holds no MAC started one `ip -6 neigh` per IA (up to 16 per packet), now one per message; the network and broadcast addresses can no longer be reserved.
  - GUI: error messages showed "true" or single letters (network errors, HTML error pages); the live refresh of the logs, the map retry and the live ping went on after leaving the page; a filter change in the proxy logs could be overwritten by an older refresh; numbers like `1e3` or `0x10` in record data and an empty TTL were accepted; passkeys made on iPhone and iPad were named "Mac"; a second step-up dialog left the first one hanging; downloads could be dropped by some browsers.

## 1.1.0 — 2026-11-14
- **Upgrading from 1.0.1:** run `manage.py migrate` (0018 to 0031; on SQLite 0029 rebuilds the log table, on PostgreSQL 0031 needs the `pg_trgm` extension and, on a partitioned log, locks writes while the index is built: pick a quiet time), then `manage.py rebuild_stats` once, then restart `rundns` and gunicorn. Before restarting: clients outside the private networks (global IPv6 addresses, a VPS) must be listed in `DNS_ALLOW_QUERY` or they get `REFUSED`; copy `deploy/nginx/dns.example.lan` again and reload nginx.
- **Security** (changes from 1.0.1):
  - **Who may ask: `DNS_ALLOW_QUERY`** (default: private, loopback and link-local networks, IPv4 and IPv6). Every other client gets `REFUSED`, not logged: the daemon listens on `0.0.0.0` and answered anyone, so a firewall mistake made it an open resolver. Clients with public addresses (global IPv6, a VPS) must be listed; `*` = anyone.
  - Adding or removing a second factor while signed in asks for an existing one (step-up, scope `mfa-change`, header `X-MFA-Grant` / field `grant`): a stolen session alone could replace the authenticator with the attacker's.
  - Wrong passwords lock the address, and the user only for that address (10 in 5 minutes); the user everywhere only after 100 in 5 minutes. Before, ten wrong passwords from anywhere locked the owner out. Behind the proxy the address is the last `X-Forwarded-For` entry (the one nginx adds), not the first, which the client chooses.
  - `DEBUG` is off unless the `.env` says `DEBUG=true`.
  - `/api/docs/` and `/api/schema/` are for staff only (Django admin session or token).
- Geolocation: each row of *Most contacted networks* has a *Log* link that opens the query log filtered by that network (new `asn` filter of `/api/logs/` and `/api/logs/grouped/`, like `country`: the domains with an answer address of the network in the period).
- Geolocation: the map shades the countries on a logarithmic scale, so when one country has most of the traffic the others are still told apart.
- Geolocation: every country and network shows its share of the queries answered with an address; the country list has a search (name, code or one of its domains) when there are more than 8; the *Destination addresses* tile says how many are located while some are still pending; the headings show how many countries and networks are listed.
- Statistics: an *Answers* panel splits the queries of the period into *with an address* (the total of the geolocation page), *without an address* (HTTPS, PTR, TXT, an AAAA for a name without IPv6...), *name does not exist*, *blocked* and *failed*, with the share of each; an *Errors* tile next to *Blocked*. New hourly counter `answer` (API: `by_answer`). Hours saved before the update show as *not split yet* until `manage.py rebuild_stats` is run once.
- Geolocation: when the period held hours saved both before and after the update to `GeoStat.first` (migration 0030 without `rebuild_stats`), the older hours counted 0, so the countries and the total were much smaller than the query log. Those hours now count every address, as the note on 0030 says; `rebuild_stats` still makes them exact.
- DNS daemon: a UDP answer is packed once (it was packed to measure it, then again to send it), and dnslib no longer prints two lines per query to stdout (request and reply; only truncated answers and errors are printed now, the query log keeps every query).
- Query log: *Load more* pages by the last row shown (`before=<id>`, keyset) instead of an offset: deep pages read only their own rows, and rows logged meanwhile no longer bring back rows already shown. `count` stays the total of the filters; `offset` still works.
- PostgreSQL: a trigram index on the log names (`qlog_name_trgm`, migration 0031, extension `pg_trgm`) makes the log search fast. Skipped, with a message, when the database user cannot create the extension. On a partitioned log the index build locks writes: migrate at a quiet time.
- Geolocation: a query was counted once per address of its answer (four A records = four), in the total and in every country, network and city, so the numbers were larger than the query log and the statistics and the shares were skewed towards names with many addresses. Now each query is counted once, at its first address (the one the client connects to: new `GeoStat.first` counter), so countries and networks add up to the total; the tile says *Queries answered with an address* (blocked, NXDOMAIN and answers without an address are not counted). Needs `manage.py migrate` (0030) and then `manage.py rebuild_stats` once: until then, hours saved before the update still count every address.
- Performance of the DNS daemon: a warm query no longer touches the database. Every query outside the zones read the DHCP name settings (`Setting`) from the database even with DHCP off: they are now read with the zones when the data changes. The database ping before each query (`conn_health_checks`) is done only after 30 s of idle time. With Redis the change counter is read at most every 0.2 s instead of up to six times per query. The longest matching zone is found with one set lookup per label instead of a scan of every zone. The blacklist memory drops the least recently used names instead of emptying itself at 20000. `main_domain` is cached. With `DNS_DNSSEC=true` the DNSKEYs of a signer zone are kept for their TTL (at most an hour) instead of being asked upstream for every validated answer.
- Query log: `grouped?by=name&ordering=count` failed with error 500 once the hourly counters had rows. The *country* filter is cached for 60 s and limited to the 5000 most asked domains (the limit was documented but not applied). The statistics over more than a day are cached 5 minutes instead of 30 s. Purging old counters updates the totals with one query instead of one per client. The single-column index on `QueryLog.domain` is dropped: the `(domain, time)` index already covers it, and every log row wrote one index less. Needs `manage.py migrate` (0029; on SQLite it rebuilds the log table: do it at a quiet time). README: optional trigram index for the log search on PostgreSQL.
- DNSSEC validation (`DNS_DNSSEC=true`, RFC 4034, 4035, 6605, 8080): validates `RRSIG` records on upstream answers through the chain of trust (RSA/SHA-256, RSA/SHA-512, ECDSA P-256/P-384, Ed25519; SHA-1/256/384 DS digests). A zone's keys are trusted only when its `DNSKEY` RRset is signed by a key matching a `DS` of the parent, itself signed by the parent's trusted keys, up to the IANA root trust anchors (KSK-2017, KSK-2024); keys found in an answer are never trusted by themselves, and a zone may sign only names inside it. `AD=1` only when every RRset of the answer is signed so; `SERVFAIL` on bogus unless the client sets `CD=1`; a delegation without `DS` is passed on without `AD`. Trusted keys are kept for their TTL (at most an hour). Limit: the absence of a `DS` is not proven (no NSEC/NSEC3 check), so a forged "no DS" turns a signed zone into an unsigned one (no `AD`) rather than bogus.
- Per-client DNS query rate limiting (`DNS_RATE_LIMIT`, `DNS_RATE_WINDOW`): refuses queries over the per-window threshold with `REFUSED` (logged as `blocked` / `rate limit`). When its table of clients is full the least recently seen one is dropped, so a flood of forged addresses cannot reset every counter.
- Dynamic DNS updates (RFC 2136, `OPCODE=UPDATE`), signed with TSIG (RFC 8945): add or delete records with prerequisite checking (failure codes of RFC 2136 §3.2.5: `NXDOMAIN`, `YXDOMAIN`, `NXRRSET`, `YXRRSET`) and automatic zone serial bump. Every update must be signed with a key of `DNS_UPDATE_KEYS` (`name:base64secret`, hmac-sha256 / hmac-sha512; `nsupdate -y hmac-sha256:name:secret`): an address can be forged over UDP, and DoH / DoT clients all reach the daemon from 127.0.0.1. The answer is signed too, a replayed message is refused, no key = updates refused; `DNS_UPDATE_ALLOW` (IPs or CIDRs) narrows down the senders further. The address and the key are checked before the zone, so an unauthorised client does not learn which zones exist. A message is applied whole or not at all. Records with no data (prerequisites, deleting a whole name or RRset, `nsupdate ... delete name`) are read too: dnslib refused them, so those updates got no answer.
- DHCP: `manage.py rundhcp` runs, as set in `.env` or the GUI (`GET`/`PATCH /api/dhcp/settings/`; everything is off by default; turn off the router's own DHCP server first, two servers on one network conflict).
  - DHCPv4 (RFC 2131, 2132, 3046, 3118, 3203, 3396, 3397, 3442, 4388, 4702, 6842): range, router, DNS servers, domain, lease time with T1/T2, fixed addresses by MAC (`DHCP_RESERVATIONS`), clients told apart by their client identifier (option 61, RFC 6842), an address is probed via ARP (`AF_PACKET` on `DHCP_INTERFACE`) and ICMP `ping` before it is offered and one that answers stays out of the pool for ten minutes (`DHCP_PROBE`, RFC 2131 3.1.2), standby failover delay (`DHCP_FAILOVER_SECS`), Leasequery (RFC 4388), authenticated `FORCERENEW` (RFC 3203 / RFC 3118 HMAC-MD5 per-client Reconfigure Key, option 90), offers held a minute, declined addresses kept out for ten minutes, leases that ended a week ago forgotten. Options sent when the client's parameter request list names them: NTP (42), search list (119, RFC 3397), classless routes (121, RFC 3442, default route added), MTU (26), PXE server and file (66, 67), encrypted resolvers of `DNS_DDR` (162, RFC 9463). Relay agents and several networks (`DHCP_SUBNETS`, JSON): the scope is chosen by `giaddr`, the reply goes to the relay on port 67, option 82 is echoed (RFC 3046). Client FQDN (81, RFC 4702) is answered with N=1: nobody updates the DNS, this server does it. A client with no address yet and no broadcast flag gets the reply straight to its hardware address when `DHCP_UNICAST=true` (Linux, `CAP_NET_RAW`, RFC 2131 4.1), else a broadcast.
  - DHCPv6 (`DHCP6=true`; RFC 8415, 3633, 3736, 5007): normal (`IA_NA`) and temporary (`IA_TA`) addresses (`DHCP6_POOL`) and delegated prefixes (`DHCP6_PD_POOL`, `DHCP6_PD_LEN`, `IA_PD`, with optional kernel route installation via `DHCP6_PD_ROUTES=true`) with Solicit, Advertise, Request, Confirm, Renew, Rebind, Reply, Release, Decline, Information-request, Leasequery (RFC 5007), authenticated Reconfigure (RFC 8415 §20.4 HMAC-MD5 Reconfigure Key, option 11/20), server preference (`DHCP6_PREFERENCE`, option 7) and rapid commit; Relay-forward / Relay-reply (nested too, interface-id echoed); DNS servers (23), search list (24), information refresh time (32) and the DNR option (144). Without a pool it is stateless. The server identifier is a DUID-UUID. At most 8 IAs of each kind are answered per message and a client holds at most 16 addresses (or prefixes): a single client could otherwise empty the pool with a few packets.
  - Router Advertisements (`DHCP_RA=true`; RFC 4861, 8106, 9463): RDNSS, DNSSL, the prefix of `DHCP6_PREFIX` (optional SLAAC) and the DNR option, every `DHCP_RA_INTERVAL` seconds and on a Router Solicitation (not more often than every 3 seconds). Router lifetime is 0 by default: this host does NOT become a default router (`DHCP_RA_ROUTER_LIFETIME`).
  - DNS: the server answers `<client host name>.<DHCP_DOMAIN>` and the reverse name of a leased address from the leases (`DHCP_NAMES`; the query log says `DHCP lease`). `wpad`, `isatap`, `localhost` and similar names are refused (a client called `wpad` would hand every browser its proxy), and a name held by another client with a live lease is not given to a newcomer (no device can become `nas`).
  - GUI: the DHCP page lists the leases (addresses and prefixes, search, ended ones, end a lease) and edits the DHCPv4, DHCPv6 and Router Advertisement settings (`GET /api/dhcp/leases/`, `DELETE /api/dhcp/leases/<4|6>/<id>/`, `GET`/`PATCH /api/dhcp/settings/`). The Django admin has *DHCP leases* and *DHCPv6 leases*.
  - Needs `manage.py migrate` (0023, 0024, 0025, 0026), the right to bind UDP 67 and 547 (INSTALL.md) and `CAP_NET_RAW` for `DHCP_UNICAST` and `DHCP_RA`.
  - Tested: synthetic packets for every message above, ARP probe and L2 unicast frames, and the real UDP sockets on the loopback interface (a DHCPv4 Request got its Ack, a DHCPv6 Information-request its Reply). Not tested on hardware: a physical client or router, the multicast group (ff02::1:2) and the raw ICMPv6 socket of the Router Advertisements.
- DDR (RFC 9462) and encrypted DNS. `_dns.resolver.arpa` is answered here and never goes upstream (the upstream answered SERVFAIL, shown as Error in the query log). `DNS_DDR` (e.g. `dot:dns.example.lan@192.168.1.23 doh:dns.example.lan/dns-query{?dns}`) announces your encrypted resolvers in the SVCB answer (with address hints), so clients that support DDR (Apple, Windows, Android) switch to them; empty (default) = NXDOMAIN. DNS over HTTPS is served by the app itself at `/dns-query` (`DNS_DOH=true`, RFC 8484, GET and POST; it passes the query to the daemon over TCP, `DNS_DOH_BACKEND`; only queries, opcode QUERY, are passed on); DNS over TLS through nginx (`deploy/nginx/dns-dot.conf`, port 853). `manage.py check_ddr` asks each announced resolver a real query over a verified TLS connection and fails if one does not answer. Limits: DoH has no login, so restrict `/dns-query` to your network (the nginx example does); the query log shows DoH clients as 127.0.0.1 (the daemon sees the app, not the client). DNR (RFC 9463): `manage.py dnr_options` prints, from `DNS_DDR`, the DHCPv4 option 162, DHCPv6 option 144 and IPv6 RA option 144 (hex; `--format dnsmasq` or `--format kea` print only that configuration, ready to save to a file) for your DHCP server or router, so clients learn the resolvers from the network before asking anything; a resolver without `@ip` hints is announced by name only (also in the RA), and this server answers the `_dns.<name>` SVCB query that follows. Multicast, loopback and unspecified addresses in `DNS_DDR` are refused (clients discard them). The layout was checked field by field against the figures and text of RFC 9463 sections 4 to 6. Limits: this app is not a DHCP server, it only produces the options; it was not tested against a real DHCP server or client (the dnsmasq `option6:` line and the Kea `code`/`space` entries follow their documentation from memory: check them with your version); the RA form is left out for a resolver with only IPv4 hints; a DoH entry takes its hints after the path (`doh:host/path{?dns}@ip`). Restart the daemon and gunicorn. The query log also shows the response code in each row.
- Query log, live refresh and hourly domain rollup (`DomainStat`, migration 0026): the page refreshed every 3 s with `setInterval`, so a slow request (the grouped view over a long period) was overtaken by the next one and they piled up on the server and the database. Now one refresh at a time, none while the browser tab is hidden, and the wait grows with the time the last refresh took (at least 3 s, three times the request). The list no longer reads the `answers` column of every row (it does not show it), and the grouped view over long periods reads the hourly `DomainStat` / `StatCount` counters instead of scanning millions of log rows.
- Public lists, faster with millions of domains. `import_blocklist` writes only what changed (domains added, removed or moved to another list) instead of deleting and re-inserting every row: on a test table of 1.3 million domains with 1% of them different, 8 s instead of about 84 s (SQLite; the transaction is small, so the table is not locked for long). Two composite indexes replace the two single ones on `source` and `list_name`: `(source, name)` and `(list_name, name)`, so the sorted, paged list (and a deep page: 0.48 s to 0.01 s) is read from the index and not sorted. The counts per list are cached and emptied by every import; no search = no count over the table; a search is counted up to 100000 and the admin search on public lists is "starts with". The table is **not** partitioned: the daemon reads it by exact name through the unique index, a partition would not shorten that, and the table fits in memory. Needs `manage.py migrate` (0022; it builds two indexes on a large table: do it at a quiet time).
- Blacklist, per list: every imported domain remembers its public list (`list_name`; the first list that has it). `BLOCKLISTS` takes `name=url` (a plain URL is named after its file). The query log says which list blocked a name (`blacklist ads.example (hagezi-tif)`, `(personal)`, `(pattern ...)`), and Public lists shows each list with its count (click a list name to see only its domains; the master switch turns all of them off). Existing entries get their list name at the next `import_blocklist`. Needs `manage.py migrate` (0021).
- Blacklist, patterns and temporary entries: a personal entry can be a regular expression (`regex`, matched with `re.search` on the queried name, e.g. `^ads?\d+\.`; a pattern Allow beats everything, a pattern block applies when no domain entry matched), and an Allow can last 1 hour, 1 day or 7 days (`expires`; ignored afterwards, up to `DNS_DATA_TTL` late). A bad pattern is refused (200 characters at most); a pattern with nested repeats, a repeated alternation (`(a|aa)+`) or a backreference is rejected to prevent ReDoS, in the API and in the Django admin.
- `scan_trackers`: a domain whose chain ends on a tracking pixel (an image under 200 bytes, or an empty 204) and sets persistent / cross-site cookies is matched too, not only the ones that redirect to another domain.
- Blacklist: **exceptions** (Allow). In Personal blocks, next to Block, and from the query log (an Allow button on blocked rows and groups): the domain and its subdomains are never blocked by the public lists or by CNAME cloaking; the longest entry wins, so a block on a host inside an allowed domain still blocks it. A name that already sits in a public list can now be blocked or allowed by hand (the personal entry takes its place and the next import skips it). Needs `manage.py migrate` (0020).
- Blacklist: **suggestions**. Personal blocks lists up to 50 names asked for in the last 7 days that look like ads or trackers (a label such as `ads`, `track`, `pixel`, `telemetry`, `metrics`, or a domain registered less than 30 days ago according to RDAP), not blocked, not allowed, not in your zones, from the hourly counters (the 5000 most asked names), each with a Block button. A hint to confirm one by one. `GET /api/blocked/suggestions/?days=`.

Run it nightly from cron (INSTALL.md now says so). CNAME cloaking: a forwarded answer whose CNAME chain points at a blacklisted name (`metrics.site.example` → `x.tracker.example`) is now blocked as well, logged as `cname <target> -> blacklist <entry>`. Restart the daemon.

## 1.0.1 — 2026-11-08
- RFC 6303: reverse lookups (PTR) of private and special addresses (10/8, 172.16/12, 192.168/16, 100.64/10, 169.254/16, 127/8, `fc00::/7`, `fe80::/10`, `::1`) that no zone answers get NXDOMAIN from the daemon, with the `aa` flag and an SOA, and never go to the upstream (routers often answer SERVFAIL). `DNS_LOCAL_REVERSE=false` turns it off. A local reverse zone still answers first.
- Deleting a zone needs a second factor (authenticator code or passkey) from the already signed-in user, no password: step-up endpoints `/api/mfa/stepup/…` give a one-use grant (2 minutes, one zone) that `DELETE /api/zones/<id>/` requires in `X-MFA-Grant`. Users with no second factor are not asked.
- Zones can be switched off and on one by one (`enabled` flag; switch next to the zone name in the GUI, and in the Django admin): a disabled zone and its records are kept but not served, its names are answered as if the zone did not exist; the GUI shows its records as disabled and read-only. Needs `manage.py migrate` (0017).
- Master switch for the Public lists too (`GET`/`PATCH /api/blocked/public/`): off = the imported domains are kept but ignored and shown as disabled; the Personal blocks keep working. At once, no new migration beyond 0016.
- Master switch for the Personal blocks (GUI, top of the page; `GET`/`PATCH /api/blocked/personal/`): off = the blocks added by hand are kept but ignored, the imported public lists keep blocking. Takes effect at once. Needs `manage.py migrate` (0016).
- Personal blocks can be switched off and on (`enabled` flag, GUI switch and Django admin): a disabled block is kept but does not block. Needs `manage.py migrate` (0015).
- Internal zones are authoritative: a name missing from a zone gets NXDOMAIN, a name without that record type gets NODATA (empty NOERROR), both with `aa` and a generated SOA (RFC 2308) instead of going to the upstream; `SOA` queries at the zone apex are answered. **Behaviour change:** names under an internal zone that have no record are no longer forwarded; `DNS_AUTHORITATIVE=false` brings the forwarding back.
- A CNAME that points to a name in our own zones now also returns the target's records (e.g. `www CNAME @` answers with the apex A record).
- Zone records can be sorted by type, host, IP / value (IPv4 numerically, then IPv6 and names) or TTL, ascending or descending.
- Statistics: the chart follows the chosen period (per minute for the last hour, per hour for 24 h, per day for 7 and 30 days: 7 and 30 bars, today included, days in the browser's time zone), with empty buckets shown as zero. The stats API takes an optional `since`. API: `per_hour` replaced by `series` + `step`.
- Static hosts (like `/etc/hosts`): exact names answered with fixed IPv4/IPv6 addresses before zones, blacklist and upstream; GUI page, API (`/api/hosts/`) and Django admin; loaded in the in-memory/Redis copy and refreshed on every change. Needs `manage.py migrate`.
- Prefetch: cached answers that are about to expire and still asked for are renewed in the background (`DNS_PREFETCH*`); cached TTLs now count down.
- Query log written in batches by a background thread (`DNS_LOG_FLUSH`, `DNS_LOG_QUEUE`): answers no longer wait for the database write. Needs `manage.py migrate`.
- Persistent database connections: the DNS daemon uses a fixed pool of worker threads (`DNS_WORKERS`) that keep their connection open, `DB_CONN_MAX_AGE` and connection health checks for the API.
- One persistent, shared Redis connection pool per process (`REDIS_POOL_SIZE`): the daemon no longer opens a connection per query.
- Zones, records and blacklist answers stay in the DNS daemon's memory until the data changes (change counter in the database and in Redis, `DNS_DATA_CHECK`, `DNS_DATA_TTL`; with Redis a change shows at once and a restart is warm): fewer database reads per query. Needs `manage.py migrate`.
- Several upstream resolvers with failover (`UPSTREAM_DNS=a,b`), and stale answers served from the cache when all are down (`DNS_STALE_TTL`).

First release of Zones.dns (backend and frontend share the version).

### DNS daemon
- Internal zones (forward and reverse) served from the database; everything else forwarded to `UPSTREAM_DNS`, with an upstream answer cache (Redis or in-process).
